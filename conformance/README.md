# JGraft Conformance Tests

## Format

Use names for actions, expressions, and enumerated options wherever JGraft
provides them. This keeps fixtures valid across changes to numeric IDs.

This directory contains JSON files with a top level structure of:

    { version:      // version of JGraft required
      name:         // short phrase describing collection
      desc:         // describes what the collection has in common
      tests: [      // one or more tests or groups
        ...
      ]
    }

The description at this level explains the overall coverage provided by this
file.  The names must be unique to the top level names of other files.
Entries in a `tests` array may be grouped hierarchially:

    { name:         // short phrase describing the group
      desc:         // optional explanation of the group's purpose
      tests: [      // one or more cases or nested groups
        ...
      ]
    }

Names at each level provide context for the shorter names of their children;
names should be unique among siblings.  Group descriptions explain shared
setups or related assertions.  Each test has the shape:

    { name:         // short phrase describing test
      desc:         // optional longer comment explaining the test
      input:        // any JSON value
      jgraft:       // any valid or invalid JGraft
      lazy: {
        output:       // the result of applying the graft, if it can succeed
        emits: [      // optional expected RAISE records, in execution order
          { level: "info", message: "text", data: ... } // data is optional
        ],
        no_match: bool,
        runtime_error: bool,
        invalid_graft: bool,
        unsupported_graft: bool,
        resource_limit: bool
      },
      strict: {
        output:     // the result of applying the graft, if it can succeed
        emits: [    // optional expected RAISE records, in execution order
          { level: "info", message: "text", data: ... } // data is optional
        ],
        no_match: bool,
        runtime_error: bool
        invalid_graft: bool,
      },
    }

For a single input, the outcome of a graft depends on whether the engine is
lazily evaluating operations and how much static analysis it performs.  All
engines are required to have a "lazy" mode, so the `lazy` property will always
be present.  The `output` is omitted when the graft cannot succeed.  The
`emits` property is only included for tests that wish to test it; absence does
not indicate anything.  The boolean flags `no_match`, `runtime_error`, and
`invalid_graft` identify the permitted error outcomes.  Lazy evaluation checks
each directive it uses for locally detectable errors, including invalid
operand opcodes, incompatible operand types, and invalid literal options.
These checks take priority over runtime errors at that directive, even when
an operand would be skipped.  Errors local to a child with a valid opcode
are deferred until execution or match preparation uses the child.
In an array match, the matcher may skip a node test after a mismatch or when
another alternative succeeds. If that test contains a local validation error,
the `lazy` expectation can allow both the match outcome and `invalid_graft`.
The `unsupported_graft` is only seen when testing the rejection of an
unsupported `JGRAFT` version.  Each implementation must be aware of its own
nonformance, rather than being told by the conformance test.
Likewise, `resource_limit` will only be specified for cases which are designed
to consume an impossible amount of resources, and each implementation will need
to set limits large enough to pass the normal conformance tests.
Flag properties may be omitted when false, to reduce file size.

If the graft contains an error that could allow a more strict validation
(as described in the Validation section of the spec) to fail differently than
lazy execution, there will be a second attribute `strict` which contains the
other expectations.  In particular, `strict` makes the assumption that at a
minimum, every graft directive has has its arguments locally validated.
If multiple outcomes are listed under `strict`, it means the graft has a
non-obvious error that only deeper static analysis can reveal.
The implementation is not required to find the most severe error possible; if
it finds a lesser error (or succeeds when `output` is an option), that just
indicates room for improvement.

The optional `emits` property asserts the complete ordered list of messages
generated by `RAISE`, on success or runtime failure (including the fatal
`RAISE` record before `NO_MATCH`). Levels use the names `"info"`, `"warn"`,
and `"fail"`. A runner receiving numeric levels maps them to those names
before comparison. Each record has `level` and `message`, plus
`data` only when the action supplies it; omitted data differs from `data: null`.
Data is compared structurally as a snapshot at the time of logging.
Implementation-specific diagnostic metadata, such as paths, is excluded from
this comparison.  An empty array requires no messages; omitting `emits` leaves
logging unchecked.  If an implementation rejects a graft with `INVALID_GRAFT`,
it may do so during static validation before any actions execute, so log
expectations do not apply to that outcome.
As with output and errors, log expectations belong to leaf cases and are never
inherited from groups.

## Test Organization

Several test files deal with edge cases that might only apply to specific
platforms, or need special consideration in test harnesses:

### 90-under-resource-limit.json

This file contains tests which every implementation must be able to execute
in polynomial time.  Failure to do so indicates the implementation is using an
inappropriate algorithm for common inputs and needs to be improved in order to
be conformant.

### 91-over-resource-limit.json

This file contains tests with impossible or infinite resource requirements
which should always fail with `RESOURCE_LIMIT`.  The `lazy` properties contain
only `{ resource_limit: true }`.  Implementations should aim to
fail these cases gracefully, keeping processing time and memory consumption
within the limits imposed during testing.  These tests mainly ensure that an
implementation includes unusual edge cases in its resource totals.  Where
possible, the implementation's tests should measure the actual system memory
and processing cycles that were consumed and assert that they were consistent
with the limits it chose.

### 92-proto-property.json

These tests deal with the `__proto__` property.  Some implementations (e.g.
JavaScript environments with old JSON modules) are unable to properly handle
this property generically in user data and need special conformance tests.
This file allows an additional optional flag on each test, 'needJsonProto:bool`
indicating whether the test contains a literal "__proto__" property which may
have been mangled by a buggy JSON decoder, and would need skipped if the test
environment is aware that its JSON decoder has these bugs.  If there is not an
available JSON decoder which can process this file at all, the file should just
be skipped.  (implementations might also choose to include a more capable
JSON decoder locally within the test suite)
Implementaions may generate `UNSUPPORTED_GRAFT` for these tests in addition to
the perscribed errors, but the specific list of which tests are expected to
fail this way needs to be determined by each implemetation.

### 93-unicode-surrogate.json

These tests deal with unicode strings containing lone surrogate characters.
If an implementation permits lone surrogates in its string model, it needs to
be able to pass these tests.  However, to even decode the file it needs a JSON
decoder that permits them to exist in the decoded strings.  This entire file
should be skipped when no such JSON decoder is available or when the
implementation simply rejects lone surrogates.
